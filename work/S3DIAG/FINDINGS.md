## 2026-11-16: s3c on the card (user yes, review skipped by the user)

Run `results/20261116-s3c-run-bcaef9f5/README.md`, package `77bf0cd4...`.
STOPPED by the launcher after 137 s: the same R5 line as rung 5, a new AER
CmpltTO on root port 0000:00:03.0 (kernel time 13851.76 s; sysfs CmpltTO 2).

KNOWN (live lines in `serial.log`): every step up to the attach finished
(LIVE steps 1-10, last at 1286343 us), then `LIVE step=11 us=1300192 a=1`:
GP_PUT 1 written. No GP_GET poll line followed; the first one was due 100 ms
later. The GPFIFO entry held only the object bind (2 words).

INFERRED: the card stopped answering host reads within 100 ms of the first
GPFIFO entry on the GR runlist channel, before any compute method beyond the
bind. The launch words of rung 5 are not the cause: the fault is in the first
schedule of this channel on GR (context load by FECS, the patch list applied on
first load, the channel or instance set-up). The S1 and S2 channels on the CE0
runlist consumed their entries with the same USERD and GP_PUT path.

`s3d` and `s3b` fetch a longer prefix of the same entry, so they would stop at
the same point: not run.

Difference found, not tested: Nouveau maps the page pool, the bundle buffer and
the patch list ("mmio list") of each GR channel with PRIV set
(`gf100.c:384,401,410,464`, `vmmgf100.c:259,315`); our PTEs never set PRIV
(`src/memstage/ChannelImage.cpp` `userdPte`). PRIV restricts access, so this
is an unlikely cause of a hang (INFERRED).

Next (read-only, no card): compare the first GR channel submission of the
rung 1 trace (`reference/linux-run-ladder/mmiotrace.txt.xz`) with our attach
and submit: the context-switch registers and FECS methods Linux uses before or
at its first GR channel schedule.

## 2026-11-16: the Linux trace around the first GR channel schedule

Source: `reference/linux-run/mmiotrace.txt.xz` (S3 reference run; the job
channel is channel 2, instance at BAR3 offset 0x103a3000, MAP 22).

Same as ours (KNOWN):
- Host registers. Between the golden-context unload (last 0x409b00 read, line
  730273) and the attach (line 892359) Linux touches GR only to read 0x17e91c
  and 0x17e920 for the patch list; the rest is timer and thermal interrupts.
  After the attach it writes no GR or FIFO register before the job: only BAR3
  page-table writes for Mesa's buffers.
- Golden generation ends with the context unload (0x409b04 bit 31 cleared,
  0x409000 = 0x100, poll 0x409b00), as `tools/gr/model.py` `generate()`.
- The patch list: 36 pairs, the same registers in the same order as our
  `patchList` (lines 811337-811410); header words 0x00 = 0x24 and
  0x04 = list address >> 8 (lines 892191-892192), as our attach hook.
- RAMFC words, except the two below (lines 615146-615160).

Different (KNOWN), cause of the hang not shown:
1. Context memory. Linux copies the golden image into a new buffer of 0x4f000
   bytes (MAP 26) and points 0x210 at it (0x380004, line 892363). It zeroes
   0x210/0x214 after generation (lines 810889-810890). We point the channel at
   the generation memory itself (0x80000 reserved + image) and never zero it.
2. Page-table entries. Linux maps the page pool, bundle buffer and patch list
   with PRIV (`gf100.c:384,401,410,464`); the trace has 301 PTE writes with
   valid and PRIV bits from line 618714. Ours never set PRIV.
3. RAMFC 0xe4: Linux's user channel 0 (not privileged); ours 0x20 (privileged,
   as the S1 kernel-channel image).
4. RAMFC 0x4c GPFIFO limit: Linux 0xa (8 KiB), ours 9 (4 KiB). Size only.

INFERRED: none of the four explains a stop of host reads on its own. Items 1
and 2 touch what FECS reads on the first context load, which is where s3c
stopped. The trace cannot show what the card reads from memory.

## 2026-11-16: aligned stage s3e (host), built and rehearsed

`gr::Align` removes the differences 1-3 above; s3e = object bind (as s3c) with
all three. Difference 4 (GPFIFO size) is left: one entry fits either size.
- Copy: after the golden stage, 0x210/0x214 are cleared (`ctxgf100.c:1551-1552`),
  the image (0x4ea00 bytes, 0x409804) is copied in 16 KiB blocks into the new
  record GrChanContext (role 29, 0x4f000, zeroed first); the attach hook writes
  the two list words into the copy and points 0x210 at it.
- PTEs: page pool, bundle and register list valid + PRIV + writable (`(e&7)==3`).
  Linux sets no read-only bit on any channel PTE; our other records keep theirs.
- RAMFC 0xe4 = 0.
- Every S3 stage now allocates 27 records (the layout gained GrChanContext);
  only s3e uses it. The s3c, s3d and s3b-diag packages built earlier today
  follow the old layout: superseded, not to be run.
- Fix: `Mapper::poll` took the start of its 2 s bound from a stale clock value.
  The longer zeroing made the first poll look late in the host test. It now
  reads the clock first.
- Guard: writes into GrChanContext only while the next program write is in the
  attach stage. Validator: S3E stage, 27 records, generations of the copy.
- Host test: the simulated card decodes the state at GP_PUT on its own (copy
  equal to the golden image word for word, pointer, PTE bits, RAMFC 0xe4).
- `make check` passes; regenerated source-hash records: register provenance,
  S1MEMARENA, S1MEMMMU, S1MEMUPLOAD, S2COPY host checks.
