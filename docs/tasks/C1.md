# Task C1: Register database

Phase C: hardware database and firmware. This file is the whole task text. `make check` verifies the
checks named here. General rules: `AGENTS.md`. Paths to Nouveau files in
any output are relative to `reference/nouveau/`; line numbers are 1-based.

- Why: the Haiku driver may only use registers with a traceable source.
  This task turns the 872 register accesses of B3 into one entry for
  each register, with the name and bit fields that envytools has for it.
- Inputs: `registers/mmio_accesses.json` (do not open it: the tool reads
  it; each entry has `file`, `line`, `function`, `op`, `reg`,
  `subsystem`), `tools/rnndb.py` (written by the scaffold: run
  `python3 tools/rnndb.py 0x002100` to see what it returns, and read its
  first 25 lines), `nvkm/engine/gr/gf100.h` lines 38 to 46.
- Outputs: `tools/build_regdb.py`, `hardware/registers/<group>.yaml`,
  `hardware/registers/README.md`.
- Groups: one file for each `subsystem` value of B3. One more file,
  `pbdma.yaml`, takes the entries of subsystem `fifo` with an address
  from `0x040000` to `0x05ffff`. This gives 14 files.
- One entry for each distinct `reg` text of the group. A file is a YAML
  list of entries, sorted by `reg`:

  ```yaml
  - reg: 0x002a30 + (engn->id * 4)     # the B3 text, unchanged
    address: '0x002a30'                # 6 hex digits, or null
    name: PFIFO.ENGINE_STATUS          # from tools/rnndb.py, or null
    name_source: rnndb:fifo/gf100_pfifo.xml    # or none
    width: 32
    readable: true                     # an access with op rd32 or mask
    writable: false                    # an access with op wr32 or mask
    fields: [{name: X, shift: 0, width: 1}]    # from tools/rnndb.py, or []
    source: ['nvkm/engine/fifo/gk104.c:300']   # every file:line of B3, sorted
    status: SOURCE_ONLY
  ```

- `address` rules, in this order:
  1. `reg` starts with a hex number (`0x002100`, `0x002a30 + (engn->id *
     4)`): that number.
  2. `reg` is a call of one of the six macros in `nvkm/engine/gr/gf100.h`
     lines 40 to 45 (`GPC_UNIT(gpc, 0x0420)`): the value of the macro
     when every variable is 0. `GPC_UNIT(gpc, 0x0420)` gives `0x500420`;
     `TPC_UNIT(gpc, tpc, 0x224)` gives `0x504224`. The tool reads the
     macros from the header.
  3. Everything else (`addr`, `base + 0x10`, `NV03_PFIFO_INTR_0`): null.
- `name`, `name_source` and `fields`: `import rnndb` in the tool and call
  `rnndb.lookup(address)`. It returns `None` when envytools has no
  definition: then `name` is null, `name_source` is `none` and `fields`
  is `[]`. Do not invent a name. Do not change `tools/rnndb.py`.
- How to do it:
  - Write `work/C1/PLAN.md` (10 lines), then the tool. Write the files
    with `yaml.safe_dump(entries, f, sort_keys=False)`.
  - Start with one group (`mc`, 7 entries), run `make check`, read the
    failures, then do all groups.
  - `tools/build_regdb.py --check` writes nothing and exits 0 when the
    files are what the tool generates. The same output on every run.
  - The work directory is `work/C1` (capital C).
- `README.md`: a table with one line for each file (`mc.yaml`, number of
  entries, number with a name, number with address null); what
  `SOURCE_ONLY` means; and a section "Not named" that lists, for the
  groups `mc`, `fb`, `fifo` and `pbdma`, the addresses without a name
  and the function that uses each (from B3). These are the registers
  that phase E has to understand from the Nouveau code alone.
- The design document also lists `compute.yaml`. Do not write it: the
  compute methods are not MMIO registers and are in
  `analysis/compute_launch.json` (B6).
- Check: the 14 files; for every entry `address`, `name`, `name_source`,
  `fields`, `source`, `readable`, `writable`, `width` and `status` as the
  rules above give them; the README names every file; `--check`.
