# Macro task S1B2: Native allocation and mapping adapter

## Why

The typed memory layer has no native allocator. Connect it to Haiku without
claiming that guest physical addresses are verified VFIO device IOVAs.
This host/cardless work follows S1BOARD in the authorized review batch (ADR 007).

## Inputs

Read src/memory/Memory.*, src/os/HaikuBackend.*, tests/test_memory.cpp,
tests/test_haiku_backend.c, docs/MEMORY-CONTRACT.md, docs/HAIKU_BUILD_TEST.md,
and the selected Haiku allocator/area interfaces.
Reference facts: Haiku nvidia driver.c:939-957 uses B_32_BIT_CONTIGUOUS.
Haiku headers/os/kernel/OS.h:77 defines it as contiguous below 4 GiB.
The source tree and kernel link setup are already pinned by the project.

## Outputs

- A native DMA32 allocation entry point and an ownership/publication adapter.
- Explicit CPU/GPA/IOVA domains, alignment, bounded access, and mapping lifetime.
- Default-unverified IOVAs and default-denied publication. No invented GPU virtual mapping.
- Partial-allocation cleanup, unmap-before-free, and retained quarantine records.
- Block reuse after failed release until cleanup succeeds.
- Host fault tests, native object/link checks, and a cardless-only memory probe if feasible.
- Update documentation, source provenance, status, and work/S1B2/ records.
- Re-pin haiku-k40c-llm shared tools if tools/haiku/ changes.

## Limits

No card write, BAR access, host binding, GPU reset, root, or push.
No DMA/IOVA verification claim without a separately approved card stage.
Do not change tests/accept/ or tools/check_repo.py.

## Check

Run host tests and make check before each commit.
Run make vm-tools-test after shared-tool changes.
Link the native adapter against the matching Haiku kernel.
A cardless result is native OS evidence only. Stop and ask before retrying any reported launcher stop.
