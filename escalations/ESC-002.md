## Source facts

KNOWN / SOURCE_ONLY in the pinned Nouveau tree:

1. `nvkm/subdev/fb/gk110.c:55-65` selects the GF100 flush-page hook.
2. `nvkm/subdev/fb/base.c:225-228` programs that target during FB preinit.
3. `nvkm/subdev/fb/gf100.c:81-84` writes the DMA address shifted by eight to
   register 0x100c10. Allocation and DMA mapping precede this in
   `nvkm/subdev/fb/base.c:281-289`.
4. `nvkm/engine/device/base.c:2908-2916` finishes subdevice preinit before POST.

Programming the target is not itself evidence that a DMA transaction starts.
This finding does not establish that POST requires a pre-POST payload test.
The reference order also does not prove that a minimal new driver must arm the
target before POST. Deferring it needs its own source-backed justification.

KNOWN from the current software:

- `src/runtime/PreStart.cpp:18-23` requires a verified device address and
  pinForSubmission before any preinit callback. It programs FlushPage before
  executeRom later in that function.
- `src/memory/Memory.cpp:49-65` requires address verification and publication
  for that submission pin. `src/memory/Memory.h:58` defines visibility as
  published storage.
- `src/os/HaikuMemory.cpp:87-93` requires a real provider for publication.
  `src/os/NativeOwner.h:64` intentionally installs none.
- `docs/DMA-CONTRACT.md`, CPU/device visibility and bounded provider sections,
  prohibit treating mapping evidence as a visibility claim or arbitrary caller
  metadata as a trusted current mapping handoff.

KNOWN from S1D0RETRY: structural map coverage of retained storage passed at one
cutoff in one guest. Publication remained denied. That guest has ended.
Its witness cannot authorize an address in a fresh A7 guest. Effective coherency
and device payload visibility remain UNKNOWN. Q7 remains open.

## Design conflict to resolve

The accepted review puts POST/A7 next and D1 after POST, with no more visibility
machinery before A7. The current candidate controller instead requires the
production publication/submission contract before it can arm the pre-POST target.
I cannot connect a physical backend by pretending D0 satisfies that contract.

A source-backed separation may resolve this: an experimental arm-only reference
with fresh in-run mapping evidence, complete ownership/retention and no claim of
DMA publication. The actual transaction/visibility contract would remain D1.
However, that is a change to the current startup memory contract. It also needs
an audit of whether POST or its readiness steps can trigger use of the armed
address. Do not merely rename a submitted buffer, set verified=true, reuse the
ended D0 witness or label a physical backend hostSimulation.

## Decision requested

Should A7 introduce that separate arm-only experimental contract while keeping
D1 after POST, or retain the existing pre-publication requirement and revise the
sequence? A source-justified deferral of target arming is another possible
resolution. Resolve this before implementing the physical A7 entry point.

This is a design decision, not permission to execute A7. A later ready package
must still list exact writes, binaries, readiness tests and stop rules, followed
by an explicit yes for one write-stage run.
