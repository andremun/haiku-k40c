# ESC-001: native cardless guest startup does not reach the test job

2026-10-16. ABC1/B3-B4 native validation. Stop further VM variants in this task.

Three bounded attempts using disposable overlays of the existing Haiku
application disk failed to reach the transfer/load job within 600 seconds:

1. `build/cardless/20261016-141120`: TCG, 2 vCPU, 2 GiB. Reached package
   initialization; no guest job/expected boot marker completed.
2. `build/cardless/20261016-142252`: TCG, 2 vCPU, 4 GiB, USB tablet/controller,
   persistent-guest readiness alternative. Stopped progressing around keyboard
   initialization; no job completed.
3. `build/cardless/20261016-143330`: TCG, 1 vCPU, 4 GiB, same bounded runner.
   Also did not progress to the job; no kernel upload or driver load result.

All watchdogs cleaned up their QEMU processes; overlays and incremental logs are
retained. The base disk/variables were not modified. No physical GPU was given
to a guest. The original vm-test.sh command line was not changed.

KVM is absent (`/dev/kvm` absent, verified outside the sandbox as well). No
attempt was made to install/load KVM, use host sudo, change host drivers or
alter running model services. The exact cause of the startup stall is UNKNOWN;
it is not established as an SMP, memory-size, driver-code or hardware defect.

The pinned cross compiler works. Native backend/probe/core objects compile with
real headers, and host failure-injection tests pass. The matching kernel.so is
still unavailable; the builder deliberately exits 2 rather than linking against
a substitute. No native link/load or K40c result is claimed.

To unblock: use a known-working cardless Haiku guest (for example the manually
accessible T7610 setup), export its exact kernel and environment, and run the
commands in docs/ABC-CARDLESS-OUTCOME.md. Alternatively diagnose the local guest
startup in a separate task. Further boot changes here would violate the
three-attempt escalation rule. No push/SSH access to T7610 is assumed.

## Resolution (2026-10-18, from the opencode-haiku session)

Used the recommended known-working cardless guest: the persistent KVM Haiku hrev60207 VM of the
sibling `opencode-haiku` package (`vm/system.qcow2`), via a disposable overlay, with
`python3 tools/haiku/cardless_run.py --base <that disk> --cpus 2 --kvm`. KVM is available on this
machine. Results: kernel export `pass` (build/cardless/20261018-152513), exported
`kernel_x86_64` SHA-256 `2da9a5b98719b40a61893836fb9c9e393e92e44f470e8af2024e76d50e2d2c62`,
byte-identical to `~/haiku-cross/lib/kernel_x86_64`; `HAIKU_CROSS=$HOME/haiku-cross bash
tools/haiku/build_backend.sh` linked both probes; `cardless_run.py --driver
build/haiku/k40_cardless_probe --cpus 2 --kvm` passed (build/cardless/20261018-152628,
`k40_os: PASS`, job.exit 0, no panic). No GPU, sudo, host service or script change. The identity probe was not run.
Evidence copy: `results/20261018-esc001-native-load/` (copied from `opencode-haiku`, commit `dcfd6f2`, on 2026-10-23). A CPU/cardless result is not
K40c evidence; B2/C2/C3 hardware stages remain.
